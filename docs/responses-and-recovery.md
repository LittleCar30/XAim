### 客户端缺陷与本次修复

1. 原实现把所有 `failed` 转为同一个字符串，丢失上游 code，无法区分临时过载和永久错误。现在使用独立的 `ProviderFailure`，记录脱敏错误分类、结束事件与状态、请求 ID、重试次数与等待时间；网关可能回显凭据或私有内容，因此不直接保存原始 error.message。
2. 对服务端内部错误、限流、过载、生成超时和暂时不可用最多补试 3 次，指数退避并遵守错误对象内的 `Retry-After`；无可识别错误码只补试 1 次。超过剩余期限、预算或 10 分钟的等待不继续重试，不缩短服务端要求的等待时间。额度、认证、权限、参数、上下文及策略错误直接停止。
3. 失败生成也消耗预算。优先使用失败响应的 usage；缺失时以本轮输入估计和已分配输出额度保守计账，明确标注 estimated。该估计用于本地任务预算，不是供应商账单实测。
4. 重试保留已经成功的工具历史，丢弃失败响应所有工具，并要求执行最小操作、分块写入。普通回复正文不会被自动当成代码执行。超长临时输出默认折叠，展开后才渲染；历史中断内容仍可检查和复制。
5. 仅当外层为 completed、内层明确为 incomplete 且 reason=max_output_tokens 时，按截断恢复处理，所有工具均丢弃。其他未证明完成的冲突仍拒绝执行，并显示具体状态。没有将 failed 或 in_progress 强行当成 completed。

### 对照 Codex 与 Claude Code

- 已检查 OpenAI Codex 官方源码 `codex-api/src/sse/responses.rs` 与 `responses_error.rs`：独立处理文本、推理和函数事件；失败响应按上下文、额度、策略、过载和限流等分类；读取错误中的重试提示，不把 HTTP 200 当成生成成功。其某些未知错误也可恢复，具体策略与版本相关。

## 工具与协议差异

| 客户端/适配器 | 原生请求形式 | 会话与工具结果 |
| --- | --- | --- |
| XAim 原 OpenAI 兼容层 | `/chat/completions` | `messages`、`tool_calls`、`tool_call_id`，SSE `[DONE]` |
| XAim 新可选 Responses | `/responses` | `input`、`function_call`、`function_call_output`，语义结束事件 |
| Codex 的 Responses 接入 | Responses | 事件式输出、函数/工具项、推理项；具体客户端还会控制上下文与重试 |
| Claude Code 的 Anthropic 原生接入 | Messages | 内容块、`tool_use`/`tool_result`；第三方兼容层由服务商实现 |
| XAim 的 Anthropic 适配器 | `/messages` | 已有原生接入，本次纠正界面中“尚未实现”的旧提示 |

Chat 与 Responses 都能支持文本、流和工具调用。Responses 有独立输入/输出项、推理配置、`max_output_tokens` 和 completed/incomplete/failed 终止事件；Chat 的字段名及结束标记不同。更换协议需要完整适配，请求路径替换不足以解决问题。Responses 本身也可能发生网络中断。

### 结论与预算核对

### 已定位的客户端问题

1. **预测值低估了实际输出成本。** `task_context.rs::forecast` 只看上一轮输出，且将预计输出封顶 8,192；实际单轮上限为 32,768。第 2、4、11、14 轮实际输出分别为 27,113、24,970、24,770、19,934，而对应工具参数仅 33、538、449、460 字节。usage 没有提供 reasoning token 拆分，配置也是提供方默认强度；不能把这些 token 全部认定为高强度思考，或直接认定为网关错报。
2. **上下文缩短后，任务剩余能力被重新乐观估计。** 程序进行了 6 次不额外调用模型的 checkpoint，其中第 22 轮将输入估计从 18,723 降到 8,034。压缩可以降低后续请求成本，但无法返还过去已经消耗的 token；当前算法在压缩后重新计算轮数，缺少独立的总预算预警阈值。第 22 轮只剩 40,611，预测仍有 4 轮，所以没有进入收尾。压缩本身不是错误，预测与收尾触发的耦合需要调整。
3. **进入收尾过晚，且收尾工具不能完成剩余交付。** 第 23 轮仅余 32,415 时才进入 finishing，并立即只提供 `update_task_state` / `report_blocked`。此时尚未完成生成器和构建入口；语法检查通过又不允许继续编辑，模型只能报告未完成，无法在这个阶段补齐核心功能。
4. **“最后状态提交”没有成为终止状态。** 第 23 轮提交 `ready_for_review=false` 后，代码直接 `continue`；第 24 轮再次提交 false，又继续。两轮分别消耗 13,467 和 15,488 token，共 28,955，剩下 3,460。第 25 轮被本地拒绝。最终状态已被持久化时，应按明确的 partial 结果结束，而不是再次要求“最后一次提交”。
5. **本地预算停止被标成模型错误。** `stop_locally` 返回 `XaimError::Model`，统一错误前缀显示“模型调用错误”；编排层又将其记录为 `execution_error` / failed。日志文案容易让用户继续排查 Responses、网络或模型额度。应使用独立的 `budget_exhausted` 原因，区分本地预算、上下文、任务时限、供应商失败与功能验证失败。

候选改动只有 `gen-scene.js`（18,490 B）和 `viewer.js`（8,930 B），两份补丁的 `applied` 均为 0。隔离目录中没有 `scene.json` 或 `palace-city.html`，现有 `build.js` 仍输出旧的 `isometric-palace.svg/html`。

进一步对 `gen-scene.js` 进行只读 AST 检查：文件只有调色板、空面片数组以及 9 个几何函数定义，没有顶层建筑群组装调用，也没有场景序列化/写文件语句。模型声称“建筑群几何已实现、只差写入 build.js”，**超过了候选代码能够证明的程度**。即使把正文里的 build.js 直接落盘，里面 `require('./gen-scene.js')` 后读取 `scene.json` 的步骤仍没有对应的生成实现。

### 修复优先级与验收建议（尚未实施）

1. 将合法的最终状态提交变成单次终结操作：ready=true 进入现有验收，ready=false 保存 partial 和待办并停止。仅无效参数可在明确的次数与预算内纠正。新增回归场景：最后状态仍有待办时，只发生一次最终提交，不再发送相同请求、不丢失差异。
2. 预算预测使用近期多轮输入/输出成本及高消耗记录，去掉与实际 32,768 上限矛盾的固定 8,192 预测封顶；把运行时提示、状态工具、可用工具变化和最终提交的完整输入一起纳入预算。新增覆盖：短读文件轮之后的长输出、checkpoint 后剩余轮数跳升、未提供 reasoning 明细等情况。
3. 在只读终结前增加有独立预算的最小交付阶段，并设置与累计余额相关的提前预警。先确保“生成数据 → 生成可打开页面 → 基本交互”成立，再做屋檐/栏杆等扩展细节；明确列出核心产物，避免临近预算耗尽仍只有辅助函数。不要简单放宽最终状态阶段的任意写入权限。
4. 将供应商实测 usage、失败调用估算和本地预算占用分别显示。保留缺失 usage 时的保守保护，但清楚说明估算范围。降低输出上限时应结合任务类型、已观察输出和截断恢复；不应统一把上限压到 4K/8K，以免再次触发截断循环。
5. 验收结果标明检查范围：语法、构建/生成、产物存在与基本数据有效性、浏览器渲染/交互。未执行的项目显示未检查；用户可见摘要不能只显示一个容易误读的“通过”。完成声明与实际文件/操作证据分开保存。
6. 通过以上本地模拟和回归后，再用明确支持所选协议的网关做受控长任务验收。切回 Chat 可以作为单变量协议对照，但无法消除上述客户端预算与收尾缺陷；单纯将总预算加倍也不能修复它们。
